# Aerospace dataset selection and feasibility

**Research snapshot:** 2026-09-28. Dataset pages and download availability can change; re-check the original source and terms before acquisition or redistribution. Unknown means the cited source did not establish the fact.

## Objective and recommendation

Select one useful, reproducible first computer-vision task for AeroInspect AI while preserving the existing image audit and object-detection infrastructure. The system is an inspection aid that highlights potential defects for qualified human review. It is not an airworthiness decision or certification system.

**Recommendation: start with one-class anomaly detection and pixel localization on AeBAD-S, the static single aero-engine blade subset of the Aero-engine Blade Anomaly Detection (AeBAD) dataset.** Train using the authors' normal-only training partition; evaluate once on the official test partition, reporting image-level anomaly ranking and pixel-level localization by domain-shift condition and defect type. The dataset's authors describe changing view and illumination/background between normal training and portions of test, a useful robustness problem directly tied to borescope inspection. Do not turn its masks into box labels. The existing YOLO detection trainer is not a suitable model path for this task. The authors' benchmark implementation provides a task-aligned starting reference, but a reproducible integration and audit layer must be developed first. The paper's stated training/test protocol and domain shifts are described in its [paper](https://arxiv.org/abs/2304.02216) and the upstream [official implementation/data instructions](https://github.com/zhangzilongc/MMR).

This is the strongest publicly downloadable **aero-engine blade anomaly benchmark found in this review**, rather than proof that it is the best dataset among every aerospace collection. A second direct aircraft fuselage option, Boeing-CMU, is restricted pending an access request; FOD-A is more immediately detection-compatible but solves airport-surface debris rather than component maintenance. Keep both as credible follow-up choices.

## AeBAD-S dataset record

- **Name/provenance:** Aero-engine Blade Anomaly Detection (AeBAD), created by Zilong Zhang, Zhibin Zhao, Xingwu Zhang, Chuang Sun and Xuefeng Chen. The [paper](https://arxiv.org/abs/2304.02216) describes a research/testbed dataset for blade inspection; the [authors' repository](https://github.com/zhangzilongc/MMR) is the primary code and data-instruction source.
- **Acquisition/access:** Repository provides Google Drive and Tian Yi Yun Pan links (the latter access code `g4pr`). No registration requirement is stated in the README; Google account/host availability may affect practical access. Record the downloaded version and checksum; don't mirror or redistribute data without checking attribution/terms. The source repository explicitly states dataset CC BY 4.0 in `LICENSE-DATASET`; the code's separate license is Apache-2.0. CC BY allows adaptation and redistribution with attribution and notices, but verify that all images are covered by the dataset grant and that rights outside copyright are not implied.
- **Size/count:** AeBAD has AeBAD-S static single-blade images and AeBAD-V videos/frames from blades mounted on rotating blisks. The paper's AeBAD-S protocol has 521 normal training images and 1,639 test images (490 normal, 1,149 anomalous), for 2,160 static images. An independent 2025 paper cites 5,570 total images for AeBAD overall; whether its count treats video frames consistently is unclear, so do not conflate that figure with the static split. Recount from the acquired release and save a manifest before asserting local counts.
- **Resolution:** Not established in the original paper text/repository README reviewed here. Measure actual image dimensions from the downloaded files; never rely on dimensions from a derived mirror.
- **Inputs and annotations:** Single-blade RGB images organized by train/test and condition/anomaly directories; anomalous test images have aligned pixel masks in `ground_truth`; normal images have no anomaly mask. Directory conditions include `same`, `background`, `illumination`, and `view`; the test set includes anomaly types breakdown, ablation, fracture and groove. Labels support image-level normal/anomalous evaluation and pixel localization, not native bounding-box object detection. Exact anomaly counts per condition and exact per-class counts should be read from the official release and reconciled against masks. The directory layout and mask pairing behavior are shown in the upstream [dataset loader](https://github.com/zhangzilongc/MMR/blob/master/datasets/aebad_S.py).
- **Split/capture grouping:** Official static train/test split is documented, with a deliberately normal-only train set. The public protocol divides testing by same/background/illumination/view. Underlying aircraft/engine/component identity and repeat inspection IDs are not documented in public metadata reviewed here; whether static frames are adjacent frames or independent captures is unknown. AeBAD-V is explicitly video data and must be split/evaluated by video/sequence, never frame-randomly.
- **Advantages:** Direct aero-engine relevance; defect masks preserve localization; authors supply an evaluation method and stress unseen imaging conditions; normal-only learning fits the scarcity of labeled damaged components.
- **Limitations:** Small normal training set; single blade/component family; unknown geographic/equipment diversity and maintenance provenance; multiple samples use 1:1 replicas/3D-printed samples according to later literature; testbed imagery cannot substantiate production transfer; type and severity/repair impact mapping are not maintenance decisions; original grouping identifiers are unknown; static subset is modest and video subset requires temporal analysis. It does not cover corrosion/damage types beyond its four described anomaly labels.
- **Registration/redistribution:** Download is linked directly by the authors; account requirement unknown. Upstream states CC BY 4.0 and offers attribution permission; preserve original license, author credit, source URL and any provenance file. This report does not redistribute the dataset.

## Why this first task matters; why alternatives wait

Borescope inspection places blades at changing orientations and illumination. A one-class system that learns a normal appearance distribution and marks unusual pixels can surface areas for an inspector to review, including defect types not explicitly represented during training. This matches actual maintenance workflow better than claiming broad defect classification from a small, curated label set. The output should be an anomaly heatmap and calibrated image-level score with uncertainty/operating limits, never a repair or airworthiness verdict.

The task is anomaly detection with pixel localization, rather than closed-set classification or detection. Expected input is a single blade image; expected output is an anomaly score plus a same-size or explicitly registered heatmap/mask for review. Evaluation should include image AUROC/AUPRC and pixel AUROC/AUPRO/PRO, broken out by official domain condition and anomaly type, with false-positive examples inspected. Keep the official partition untouched. The authors use sample-level AUROC and pixel-level PRO for AeBAD-S.

The present pipeline provides reusable image validation, exact/perceptual duplicate checks, and experiment tracking. It **cannot train or evaluate AeBAD as-is**: its annotation validator expects YOLO boxes, trainer optimizes detection loss, and evaluator reports detection metrics. Reuse Phase 0 scan/duplicate/leakage logic where possible; add mask integrity (dimensions, binary/value range, matching filename, empty/foreground consistency) and an anomaly-localization evaluator. Compare an established feature-embedding anomaly method such as the paper's MMR or PatchCore only after its setup, pretrained-weight license, compute and reproducibility have been reviewed. No final architecture has been selected and no training was done for this report.

Aircraft surface/FOD datasets were not selected because their domain/task differs from blade inspection, or public data/legal terms/access could not be verified. The Boeing-CMU set is a strong direct manufacturing alternative, but its files are currently access-restricted and its CC BY-NC-SA terms are unsuitable if this portfolio needs commercial reuse. The mockup fuselage dataset has 6.7 GB of openly downloadable images but lacks visible license, official split and pixel/box labels. AGDD's paper itself says its raw canopy defects are not publicly accessible, despite repository preprocessing code. FOD-A remains the most compatible alternate if a YOLO detection milestone takes priority: it has boxes, 31 categories and explicit conditions, yet targets debris on runways/taxiways rather than engine maintenance.

## Dataset preparation plan (not executed)

No conversion script is justified yet. The AeBAD authors supply an existing directory tree, masks and evaluation loader, and changing the format before inspecting the download risks losing condition metadata or mask alignment. First run a manifest-only acquisition/inspection step; implement a converter only if the verified release cannot be read cleanly by a selected anomaly method.

1. Download the original AeBAD release to an ignored, source-only location such as `datasets/source/aebad/`; do not edit, recompress or overwrite it. Save repository commit/URL, archive name, retrieval date, size, SHA-256 and license/attribution copy in a local provenance record. Keep credentials out of the repository.
2. Inventory files, image dimensions/modes, archive members, split/condition/anomaly counts, masks and video frame counts. Compare counts against upstream's documented static split (521 train, 1,639 test) and report differences instead of silently normalizing them. For AeBAD-S, preserve original relative paths.
3. Make an immutable working copy only if needed. Phase 0 can audit image files by split without labels; store reports outside source data. Because the current CLI only treats named split folders as leakage partitions, either audit a mirror that exposes train/test folder names or invoke its Python API with a documented mapping. Run annotation validation separately until mask support exists.
4. Add a minimal AeBAD mask checker before modeling: every anomaly mask resolves to exactly one image; image/mask dimensions match; mask is readable and has expected background/foreground values; normal images do not have anomaly masks; anomalous images do; empty/full masks and corrupt files are reported for human review. Do not convert a pixel mask to a box.
5. Compare exact SHA-256 and perceptual hashes **within and across** splits. Preserve the official split; flag overlaps and potential near-duplicates. Check sequence/capture linkage in names/metadata; public documentation does not prove component identity. Do not claim group leakage is ruled out if identity metadata is absent.
6. Produce deterministic manifests (source-relative path, split, condition, anomaly type, mask path, dimensions, file SHA-256, pHash and source ID) and a preparation summary with image/mask/condition counts. Keep train normal-only and official test intact. Any development validation split must be carved only from training normals and used for threshold/model selection without using test defect labels.
7. Evaluate on the authors' official test partition once after model selection is frozen. Report image- and pixel-level metrics per shift subset and defect class, bootstrap uncertainty where feasible, false-positive/false-negative visual review, environment, seed, model/checkpoint hashes and exact manifests. Do not tune repeatedly on the test set.

If future AeBAD-V work proceeds, make a separate video manifest with video ID and frame index; assign entire videos to one split or retain the official video protocol. Deduplicate frames within sequences and do not treat neighboring frames as independent samples.

## Required production expansion

Before any operational claim, obtain governed data from multiple aircraft/engine models, operators, maintenance organizations and borescope devices; include real serviced engines, accepted/known-good variation, rare defects, noise/artifacts, repeats across inspection visits, and inspector-reviewed localization/severity/repair disposition. Ensure group identity and acquisition metadata, permitted use, independent external-site holdouts, and calibrated human-review workflows. Add severity assessment only with engineering-approved labels. Validate prospective performance with qualified inspectors and applicable quality/safety processes; this research benchmark alone cannot establish safety or airworthiness.
